### [FEATURE-022] 100% completion celebration (confetti + message)

- **Status:** Done
- **Description:** When the user completes the task that brings them to 100%, briefly show a confetti burst and the message "All tasks complete! Amazing job! 🎉" over the Today's Tasks card. Must trigger only from the user actually completing the final task — never from a page refresh where all tasks are already done, never repeatedly while sitting at 100%, but okay to fire again if the user unchecks a task and later re-completes everything.
- **Notes:** The trigger logic lives in `src/app/index.tsx`'s `toggleTask`, not as a generic "watch the percentage" effect — this is deliberate. After computing the updated tasks array, it checks `completed && updatedTasks.length > 0 && updatedTasks.every(t => t.completed)`: only true when (a) this specific action just *set* a task to completed (not uncompleted), and (b) that action happened to make every task complete. This precisely satisfies all the required behavior for free:
  - **Never on refresh**, because `toggleTask` only runs from a user tap — hydrating persisted tasks on load never calls it.
  - **Never repeatedly at 100%**, because the condition requires `completed === true` for *this* toggle — once everything is done, the only tasks left to tap are already-complete ones, and unchecking one sets `completed = false`, which fails the guard.
  - **Never from deleting the last open task**, because `deleteTask` is a separate function with no celebration logic at all — only completing a task can trigger it.
  - **Fires again after uncheck → recomplete**, because it's re-evaluated fresh on every `toggleTask` call with no "already celebrated" flag to block it.
  - On trigger, `isCelebrating` is set true for `CELEBRATION_DURATION_MS` (2200ms, via a `setTimeout` tracked in a ref and cleared on unmount/retrigger) then automatically reset — passed down to `TaskCard` as a prop, which renders the confetti + message overlay conditionally.
  - New `src/components/confetti-burst.tsx` (`ConfettiBurst`) implements the confetti using only React Native's core `Animated` API (`Animated.Value`, `Animated.timing`, `Easing`) — **no new dependency**, since a third-party confetti library risked incompatibility with this project's bleeding-edge Expo SDK (per the "Expo HAS CHANGED" guidance already encountered a few times this project). ~16 small pastel squares (colors drawn from the existing `accent`/`mint`/`peach`/`purple`/`backgroundSelected` tokens) are laid out as plain flex children in a row (not absolutely-positioned percentage coordinates, which don't type-check cleanly against `DimensionValue` in this project) and animate falling/drifting/rotating/fading via `transform`/`opacity` only.
  - The message renders as a pastel `accent`-colored pill centered over the card. Both the confetti and message overlay are `pointerEvents="none"` so they never block taps, and `TaskCard`'s outer card gained `overflow: 'hidden'` so the effect stays visually contained within the card rather than bleeding onto Pet Progress/the living room below — this does not affect the three-dot menu popover, which is confirmed to render via `Modal`'s portal (`createPortal`, verified in `react-native-web`'s source) outside the card's DOM/view hierarchy entirely.
  - Adding tasks, completing/uncompleting, persistence, the tracker/progress bar, categories, icons, Mark as Important, the important star, the three-dot menu, deleting, header, living room, Pet Progress, and hatching were all left untouched. The pet reaction for unchecking a completed task was explicitly not added at the time — added separately afterward (a temporary "Aww, not done yet? You got this! 💕" speech-bubble message on uncheck, using the same timeout-ref pattern as the other pet messages).

### [FEATURE-061] Pet health: Sick, Critical, death, and free recovery

- **Status:** Done (the health rules passed 37 automated checks and the family store 47 (migration, adoption, growth split, health, resurrection, failed saves, restart) in a throwaway test run; not yet tested in the app)
- **Description:** Each pet follows Healthy → Sick → Critical → Deceased on its own timers (`src/utils/pet-lifecycle-core.ts`).
- **Notes:**
  - A pet becomes Sick when Hunger, Cleanliness or Happiness reaches 0 (several at once = one episode, one timer). 24 hours later it becomes Critical (the original sickness start is kept); 72 hours after that (96 hours in total) it passes away. Death is never instant. Growth is paused while Sick or Critical.
  - It recovers for free as soon as Hunger, Cleanliness and Happiness are all at least 50; the timers clear and a future episode starts fresh. No growth is granted for time spent sick.
  - **Energy is different:** at 0 the pet falls asleep from exhaustion (no sickness, no death) and wakes once Energy has recovered to 50; this never resets a sickness timer.
  - Egg-stage pets have no pet care, so their needs don't decay and they can't get sick.
  - **Timers use saved timestamps** and run for every living pet from the root layout (at launch, once a minute, and when the app returns to the foreground), not from the Home screen. Elapsed time is measured between instants, so time zone and daylight-saving changes don't matter; a device clock moved backwards never rewinds a pet's timers. If a need hit 0 while the app was closed, the sickness start is the estimated moment it crossed 0 (never earlier than it really could have been), or the moment of the first launch for a pet that was already at 0.
  - Home shows gentle speech-bubble messages for each state, the family bar shows a warning panel with what care is needed and a countdown, and a deceased pet's care buttons, needs bars and poop are hidden. No new sick artwork was invented.

Keys are fixed at the start of each operation and queued writes carry their own key, so an operation can never write into another profile. ### [FEATURE-088] Parent PIN and recovery code: authentication foundation (Family Cloud M2, Phase 2A-0b) (2026-11-03)

- **Status:** The PIN and recovery-code logic, native secure-storage handling and tests are implemented (299 tests in 12 suites pass). Everything is behind `FAMILY_MODE_ENABLED` in `src/utils/dev-flags.ts`, which is **false for everyone**. There is **no screen to create or change a PIN yet**, no device-authentication adapter yet (that is the next authentication phase, not started), no profile picker, and family mode must stay unavailable to real users (BUG-072, BUG-074, real-device checks below). NOT committed.
- **Dependencies (exact):** `expo-secure-store` ~57.0.4, `expo-crypto` ~57.0.4, `expo-local-authentication` ~57.0.3 (installed with `npx expo install`; NOT used yet), and `@noble/hashes` **1.8.0** (pinned exactly; audited, pure JavaScript, no native code, CommonJS and ESM; no deprecation notice; `npm audit` lists no advisory for it or for the three Expo packages). Only these 4 packages were added to the lockfile, no existing version changed, and `npm audit` stays at 48 findings (none in the new packages). `expo install` also added the `expo-secure-store` config plugin to `app.json`: it adds Android Auto Backup rules that EXCLUDE secure-store data (so the PIN record is never copied to a new phone by a backup) and a default Face ID usage string; both need the new native build. `npx expo install --check` also lists two OLDER mismatches that were not touched (expo-system-ui and expo-web-browser: expected ~57.0.4 and ~57.0.3); no dependency was upgraded.
- **Verifying a PIN:** the PIN is never stored. A record holds the key-derivation settings, a random 16-byte salt from the operating system (`expo-crypto`; there is no weaker fallback: without secure randomness setup fails) and a 32-byte **scrypt** output (`@noble/hashes`, N = 2^15, r = 8, p = 1, about 32 MiB, run asynchronously so the screen does not freeze). Settings are stored in each record. PIN and recovery code use separate domains, so one record can never verify the other, and bytes are compared in constant time. A new PIN must be 6 to 8 digits and not trivially guessable (all one digit, a straight run, a short repeated block). **scrypt was chosen over PBKDF2 (600,000 rounds took about 0.95 s in Node and is likely several times slower on a phone) and Argon2id (about 0.5 s in Node, too slow in JavaScript).** The settings measured about 0.1 s in Node; they have NOT been timed on a phone (see below).
- **Where things live:** ONE record in native secure storage (Keychain on iOS, Keystore-encrypted storage on Android, "when unlocked, this device only"): install id, PIN verifier, recovery verifier, recovery generation. The wrong-guess counter also lives in secure storage (so editing ordinary storage cannot reset it) and is shared by PIN and recovery-code guesses. Ordinary storage (which IS backed up and restored with the family data) holds only a small marker with the install id: no secret. Changing the PIN or using a recovery code replaces the single secure record in ONE write: it either fully happens or the old record stays.
- **Recovery code:** 120 random bits as 24 Crockford-base32 characters plus a Luhn check character, shown once as five groups of five. It is stored only as its own scrypt verifier. A mistyped character is caught by the check character without costing a guess (tested for every possible single-character mistake). A correct code sets a NEW PIN and returns a NEW code; the old code stops working at the moment the new record is saved (tested, including two recoveries at once: exactly one succeeds). If the new record cannot be saved nothing changes. It is independent of the PIN: the code never reveals the PIN, and a PIN change leaves it valid. It never touches any family data (checked: every ordinary key byte-identical).
- **Family data without its PIN record (restored data, a new device, damage): locked, never reset.**
  - marker + secure record agree -> normal. No marker -> no PIN (a stale Keychain item surviving a reinstall is ignored and can be replaced by an explicit setup).

### [FEATURE-097] Web single-tab protection, Stages 4.4a and 4.4b: the Web Lock state machine and the storage write fence (Family Cloud M2) (2026-11-06)

- **Status:** Implemented and tested (979 tests; 60 of them new; plain `npx tsc --noEmit` clean). **Not committed.** Family Mode is unchanged (`__DEV__` and `EXPO_PUBLIC_FAMILY_MODE=1`: off by default, impossible in a release build). **Nothing is connected to the app yet:** no screen, no startup gate and no installed fence (that is Stage 4.4c); no dependency, native configuration, Parent PIN rule, saved-data format or existing storage behavior changed. Stages 4.4c, 4.4d and 4.5 are not started.
- **The ownership rule (`web-tab-lock.ts`, 4.4a):** one browser tab at a time owns family storage, and the source of exclusive ownership is an exclusive Web Lock (`navigator.locks`, `ifAvailable`) held for the whole life of the owning document; the browser releases it when the tab closes, crashes or reloads. Nothing steals, forces, aborts or bypasses a lock, there is no "take over anyway", no heartbeat, no token and no localStorage ownership record (localStorage cannot make a check-then-write atomic across tabs, so it is not used as a lock). Fail closed: no secure context (a LAN address over http), no Web Locks, or storage that cannot be read and written (probed with an unrelated key that is removed at once) makes the tab "unsupported" and nothing may run.
- **States:** `checking`, `owned` (this document holds the lock), `blocked` (another tab does), `released` (this tab handed the lock over), `lost` (something other than this app took it), `unsupported`. `isOwner()` is true only in `owned`. A blocked tab never reads or writes family data. `start()` works once per document: a document that failed to own, or gave the lock up, never re-acquires in place, because its memory may be stale; `claim()` reloads the page and the fresh document runs `start()`, so "owned" always means a fresh document that really holds the lock.
- **Cooperative takeover (BroadcastChannel only):** a blocked tab can ASK. The owner answers through a hook the app will provide: it asks its own person when a profile is open, finishes every tracked save and leaves the profile, and answers "accept" only after that worked; anything else ("in use", "save failed", "not ready", a thrown error) keeps the lock and tells the asking tab why. On accept the owner stops being the owner BEFORE the lock is let go (so it cannot write in between), releases it, and says so; the asking tab then reloads (`claim`) and the fresh document acquires the lock. An owner that is frozen or silent keeps the lock: the asking tab only learns "no answer after 3 seconds" and waits (a frozen owner that wakes answers the old request and the handoff then completes normally). Without a BroadcastChannel asking is impossible and a second tab can only wait. A closed or crashed owner releases the lock by itself; a waiting tab learns it from a queued Web Lock request that only notices (it never reads or writes anything and never becomes the owner) and from the owner's message, with no polling, and it claims only when its person asks (or already asked). A reload retries a few times in a row, because the old page may still be letting go.
- **The write fence (`storage-fence.ts`, 4.4b):** wraps the mutating methods of the one `AsyncStorage` object every module imports (`setItem`, `multiSet`, `mergeItem`, `multiMerge`, `removeItem`, `multiRemove`, `clear`) once, for keys starting `@ProductivityPet:`; a call is refused (with `TabNotOwnerError`, which every existing writer already treats as "could not be saved") unless the lock is held at that moment. A multi-key call with any protected key is refused whole. Keys that are not ours (a library's own) and every read pass through unchanged. It is only installed by `installFamilyWebStorageFence`, which does nothing at all (and leaves the storage object exactly as it was) unless family mode is on AND the platform is the web. It does not claim to make a write atomic across tabs: the Web Lock is the exclusive owner and the fence makes this tab's code obey it; a tab that gives the lock up is refused from that moment, before the lock is even let go.
- **Proof that no write path is missed (`tests/storage-audit.test.ts`):** the application has exactly these `AsyncStorage` write sites: `profiles.ts` x5 (writeScoped for all profile and Main data, the pre-profile backup, the registry's corrupt copy, its first write, writeRegistry), `household.ts` x2 (safety copy and the household write), `onboarding.ts`, `parent-gate.ts` (guess counter), `parent-auth-backend.ts` (PIN marker), `paw-tokens.ts` and `pet-family.ts` (safety copies), `dev-stage-preview.ts` (a development tool). The audit fails when a new write path appears, when AsyncStorage is aliased, passed around, required or re-exported, when any other storage API (`localStorage`, `sessionStorage`, IndexedDB, cookies, caches, another storage library) is used in `src` (only the lock's own probe), when a literal key lacks the prefix, or when a storage module's key constant lacks it. A runtime battery (profile data, registry, household, onboarding, guess counter, PIN marker, safety copies of unreadable records) proves that without ownership not one key is created, changed or removed, and that with ownership the app writes only prefixed keys. Registry revision checks, household safety copies, tracked writes and profile-session protections are untouched.
- **Tests:** a two-tab simulation (`tests/tab-sim.ts`: exclusive Web Locks, crash, freeze, an external steal, a shared BroadcastChannel and a shared storage) covers competing tabs (five at once: one owner), cooperative handoff and its order, consent refusals, a second request while deciding, a frozen owner keeping the lock, a crashed owner, a reload race, a lost lock, no BroadcastChannel, no Web Locks, an insecure context and failing storage, plus a seeded random run of 300 operations that never shows two owners. Stale-tab writes after ownership loss, after a handoff (old owner, old document of the new owner), after an external steal, from a blocked tab, and from unsupported environments are all refused; family mode off and non-web platforms install nothing.
- **Not verified (needs the next stages and a real browser):** the behavior of real Web Locks across real tabs (the simulation models the rules the code relies on), the startup gate that keeps a blocked tab from reading or running any startup code, the screens, and the module-level onboarding load in `_layout.tsx` (still runs at import; deferring it is Stage 4.4c).

A tab that learns the lock is free (the owner closed or crashed) only SAYS so: it owns nothing, runs nothing and reads nothing until its person taps "Use this tab" (tested: no mounts, no storage reads, no reload, the lock still free). A frozen or silent owner keeps the lock; there is no forced takeover, no heartbeat and no fallback.
